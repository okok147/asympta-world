# Asympta World — Validated Agent Architecture

## Design invariant

**A language-model response is never world state.**

The model may propose a plan containing protocol actions. The runtime owns validation, execution, evidence, and state commitment. A proposed transition that cannot be proven correct is discarded rather than displayed as success.

## Layers

### 1. Conversation layer

`src/App.jsx` provides one intent field rather than workflow presets. The user can describe a purchase, service request, skill match, coordination problem, or a task that requires discovery of a new simulated participant.

### 2. Planning layer

`src/engine/planner.js` sends a compact world snapshot and user intent to `/api/agent`.

The server route:

- reads the OpenRouter key only from a server environment variable;
- routes only to approved `:free` GPT-OSS model IDs;
- prevents client model overrides;
- constrains output to a JSON plan contract;
- validates the top-level plan schema before returning it;
- applies body limits, a timeout, and basic request throttling.

When the model route is missing, overloaded, or invalid, the client uses an intent-derived deterministic safety planner. This is not a preset workflow picker: the plan is generated after the user writes an intent and references the current world state.

### 3. Protocol action layer

The complete allowlist is defined in `src/engine/validation.js`:

- `discover_entity`
- `inspect_entity`
- `move_agent`
- `send_message`
- `request_quote`
- `reserve_resource`
- `create_order`
- `prepare_order`
- `handoff_order`
- `deliver_order`
- `verify_condition`
- `complete_task`

Anything else is rejected before execution.

### 4. Validation layer

Every step passes four gates:

1. **Schema gate** — action type, parameter object, required fields, string bounds, positive quantities.
2. **Precondition gate** — referenced actors/entities exist; resources are sufficient; order lifecycle states are valid; duplicate refs are rejected.
3. **Postcondition gate** — the expected state fact is observed after applying the candidate transition.
4. **Global invariant gate** — world revision, agent locations, resource ownership, and resource balances remain consistent.

### 5. Transition layer

`src/engine/reducer.js` clones the current state, applies exactly one deterministic action to a candidate, advances the revision once, and emits one event.

The current state is replaced only when postconditions and global invariants pass. Failed candidates do not leak into the UI.

### 6. Orchestration layer

`src/engine/orchestrator.js` runs the plan sequentially and publishes progress to the interface.

Safety bounds:

- maximum 14 planned steps;
- maximum 18 committed transitions per run;
- one repair attempt after a precondition rejection;
- abort support at every delay boundary;
- fail-closed behavior after a second rejection or any candidate-state validation failure.

Repair receives the failed action, validation errors, completed steps, remaining steps, and the latest world snapshot. It cannot erase already committed history.

### 7. Evidence layer

Each ledger entry records:

- queued, validating, executing, verified, rejected, or failed-validation status;
- precondition output;
- transition event;
- postcondition evidence;
- timestamps.

The world also stores domain evidence such as inspections and `verify_condition` results. Completion is a state transition, not a message generated by the model.

## State model

The world contains:

```text
revision
entities
agents
resources
quotes
reservations
orders
messages
evidence
events
tasks
activity
```

Refs are stable protocol identifiers. Human-readable names may be translated without changing the IDs used by actions.

## Order lifecycle

```text
confirmed → prepared → in_transit → delivered
```

The validator rejects preparation without a valid order, handoff before preparation, and delivery before courier handoff. `verify_condition` then proves the delivered state before `complete_task` can describe the outcome.

## Simulation boundary

Current actions update only the local Asympta World simulation. The system deliberately does not expose tools for real checkout, payment, email, messaging, identity verification, logistics providers, or business APIs.

Future real-world adapters should sit behind the same protocol and validation boundary. A real adapter should additionally require:

- explicit user authorization policy;
- idempotency keys;
- signed receipts and tool responses;
- financial and privacy limits;
- compensating actions;
- human approval for high-impact actions;
- audit retention and revocation.

The simulation engine therefore becomes a testable foundation rather than a visual demo that implies work was completed without evidence.
